# BattleCore: автономная симуляция боя и последующее подключение Unreal Mass

Дата: 2026-11-02. Статус: утверждено пользователем командой «Делай» 2026-11-02.

## Задача пользователя

Переписать сохранившиеся механики Unity-проекта на C++ для последующего подключения к Unreal Engine и Mass. В ближайшие несколько недель разработка должна быть возможна без GUI Unreal и без установленного движка. На поле — несколько тысяч бойцов; движение и тактические решения преимущественно рассчитываются полками. Предусмотреть вселение игрока в отдельного бойца.

Пользователь разрешил реализацию автономных этапов 1–11. Этап Unreal выполняется после появления движка. Unity-исходники сохраняются.

## Подходы и рекомендация

1. **Самостоятельная библиотека C++ + консольный запуск + будущий адаптер Unreal.** Всё игровое ядро проверяется сейчас. Позднее понадобится интеграция с представлением и миром UE. Этот подход утверждён пользователем.
2. **Сразу модули Unreal/Mass.** Раньше проверяется настоящая интеграция, но для сборки нужны файлы движка, UnrealBuildTool и совместимый toolchain. При нынешнем ограничении это отложит проверки большинства изменений.

Предлагаю подход 1. На первом подключении ядро владеет состоянием, Mass обслуживает представление бойцов. Пакетные функции не привязываем к хранилищу: перенос их исполнения и отдельных данных непосредственно в Mass — отдельный, измеряемый этап после рабочего адаптера. Первое подключение не означает, что вся симуляция уже ускоряется планировщиком Mass.

## Данные и правила состояния

- Стабильные `UnitId`, `RegimentId`, `OfficerId`, `OrderId`, `EventId`; значение 0 зарезервировано как невалидное. ID отделены от индекса массива, уничтоженный ID не переиспользуется в пределах сражения.
- Боец хранит принадлежность полку, тип, здоровье/признак жизни, экипировку, место в строю, положение и режим управления. Один живой боец учитывается ровно один раз, включая управляемого игроком.
- Полк хранит центр, направление, размеры строя, назначенный маршрут, состав, мораль и действующий приказ. Отдельно хранятся неизменяемые определения типов и изменяемые состояния.
- Офицер — самостоятельная запись, связанная с полком и иерархией. Один действующий командир принимает решение о движении полка; знаменосец и музыкант не выдают дополнительные движения.
- Каждая офицерская запись ссылается на один `UnitId`: здоровье, жизнь, позиция и режим управления принадлежат этому бойцу, отдельной второй жизни у OfficerState нет. Legacy `size` считает рядовых; 200 рядовых и 3 офицерских тела дают 203 живых Unit. Все три записи относятся к полку legacy 0 и стороне 1. Во внутреннем roster учитываются и рядовые, и офицеры; для статистики отдельно доступно число рядовых и офицерских ролей.
- При импорте OfficerId назначается по строке файла, повторяющееся старое поле сохраняется как метаданные с предупреждением. Повторы ID в нормализованном JSON запрещены. Главный командир полка выбирается по рангу роли 2 > 1, затем по стабильному ID; после смерти его заменяет следующий живой командир. Роли 3/4 не принимают командование. Это мой вариант первой версии.
- Начальная симуляция плоская, высота сохраняется в данных. Единицы ядра: метры, секунды, радианы; оси X вперёд, Y вправо, Z вверх.
- Импорт Unity: `(x,y,z) -> (z,x,y) * legacy_scale`, `legacy_scale=1` м/ед. — мой начальный вариант. Угол из действующей формулы `downloadMap.cs:190-193` сохраняется как yaw. Проверить направления 0 и pi/2 на независимых геометрических фикстурах. Не переносить ошибку Vector2->Vector3 из старого поворота.
- Численность полка равна числу его живых бойцов. Смерть удаляет живого бойца из учёта ровно один раз; ID остаётся пригодным для журнала и записи повтора.

## Время, команды и исполнение

- Предлагаемый шаг ядра: 20 Гц, целый `Tick` по 50 мс. Любое значение tick_ms кроме 50 отвергается до изменения мира. Отображение позднее интерполирует между шагами; это не обещание FPS.
- Шаг: принять команды -> построить восприятие -> принять решения -> построить движение -> рассчитать боевые события -> применить результаты -> выпустить снимок.
- Входные команды имеют целевой tick и монотонный sequence. Одинаковый набор команд упорядочивается по `(tick,sequence)`, боевые события — по `(due_tick,event_id)`.
- Протокол команд включает IssueOrder, ReformRegiment, AcquireControl, ReleaseControl, MoveControlledUnit, AttackControlledUnit и ExternalPoseSample. Будущие команды остаются в очереди и входят в Snapshot; повторный sequence не исполняется второй раз.
- Некорректный формат пакета (нечисловая поза, неверный tick_ms, конфликт двух источников движения) отвергается до изменения мира и не продвигает tick. Допустимая по формату команда с недоступной игровой целью даёт CommandRejected/OrderFailed и не блокирует остальные команды шага. NoPath — результат выполнения приказа, а не повреждение мира.
- Seed и счётчики генерации случайностей входят в состояние. Цель первой серии: идентичное воспроизведение одной сборкой на одной платформе. Битовая идентичность разных компиляторов/CPU пока не обещается.
- Случайный результат привязан к `(seed,tick,phase,actor_id,event_ordinal)`, а не к порядку потоков. Итоговые события и редукции упорядочиваются по стабильным ID; fast-math не использовать в эталонной сборке.
- Команды изменения состава и владения применяются на границе шага. Во время пакетного обхода не инвалидировать ссылки и индексы.
- В горячем пути использовать массивы и пакетные проходы. Выбор SoA/AoS для конкретных полей остаётся исполнителю по замерам; нельзя плодить тяжёлые объекты с собственным tick на каждого солдата.

## Движение и навигация

Сначала реализовать строй без препятствий: линия, колонна, поворот, движение, заполнение свободных мест после потерь. Ширина задаётся числом мест в ряду и расстоянием между ними; место бойца стабильно до явного перестроения.

Затем подключить интерфейс маршрутов. Форма полка — ориентированный прямоугольник: ширина `(columns-1)*spacing+2*body_radius`, глубина `(rows-1)*spacing+2*body_radius`, body_radius=0.3 м по умолчанию, центр — геометрический центр строя. Автономный backend использует A* по `(cell,heading)` с 4 направлениями heading и 4 соседями. По умолчанию сетка 2 м; сценарий может задать другую величину. Перед прямолинейным перемещением проверяется swept rectangle, при повороте на месте — свободный охватывающий диск радиуса половины диагонали. Это безопасная, но консервативная проверка поворота. Узкая колонна проходит прямой коридор подходящей ширины; тесный угол может дать NoPath даже при существовании более сложного манёвра. Узкий проход требует явного перестроения или результата `NoPath`; полк не проходит сквозь препятствие и не телепортируется. Старт с произвольным yaw требует безопасного поворота к одному из 4 маршрутных heading, маршрут возвращает позиции вместе с yaw.

Мой baseline контактов: прямоугольники полков не проникают друг в друга. Сначала рассчитываются предложения движения всех полков, затем разрешаются конфликты. Союзники уступают по приоритету приказа, при равенстве — меньшему RegimentId; вражеские полки останавливаются перед контактом. Индивидуально атакуют только живые бойцы, досягающие цели своим оружием из фактической позиции. Порядок вычисления урона сторон не даёт преимущества. Продавливание щитами, физическая деформация строя, сложное расхождение союзных колонн и автопоиск выхода из взаимной блокировки — поздние расширения; первый вариант может ждать нового приказа при блокировке.

Это тестовая навигация для плоских сценариев. Рельеф, полноценный NavMesh UE, высотные переходы и движущиеся препятствия проверяются на этапе Unreal. Важна замена backend маршрутов через интерфейс без переписывания правил полка.

## Офицеры и приказы

- Минимальные приказы: Hold, MoveTo, Attack, Withdraw, Rally. Состояния выполнения: Pending, Active, Completed, Failed, Cancelled.
- Приказ содержит автора, получателя, приоритет, целевую точку/UnitId/RegimentId, время создания/доставки и срок действия.
- Восприятие содержит собственный полк, доступных противников/союзников и последние наблюдения с временем. Нет цели — допустимое состояние.
- Выбор действий — детерминированная оценка полезности; исполнение — автомат состояний. Переоценка раз в 10 tick, минимальное удержание решения 20 tick, немедленная реакция на смерть/недоступность цели и обязательные команды.
- Сначала 1 командир полка и явные приказы. Затем инициативность, `tacticMind`, `charisma`, `LeadDist`, `LeadSkill`, состояние морали и задержка связи. Это предлагаемый дизайн, а не утверждение о готовности старого ИИ.
- Полк без живого командира продолжает текущий явный приказ и принимает новые явные приказы, но не выбирает самостоятельное наступление. Локальная защита доступным оружием сохраняется. Смена командира не сбрасывает действующий приказ; если преемника нет, действует та же политика. Так шесть полков legacy-сценария остаются управляемыми.
- Решение пишет причины и оценки в журнал. Случайность личности вводить только после работающего воспроизводимого цикла.
- Генерал/часть/группа и видимый бегущий адъютант — последующие расширения. В первой версии задержка доставки приказа проверяется без 3D-посыльного.

## Боевые правила первой версии

Переносить понятия из старого проекта, а математические правила фиксировать явно, не воспроизводить обнаруженные дефекты.

Предлагаемый простой проверяемый baseline, который можно заменить после обсуждения баланса:

- Атака проходит фильтры: живой противник, дальность, готовность оружия; союзник и мёртвая цель не атакуются.
- Параметры оружия в сценарии: `damage`, `range`, `cooldown_ticks`, `windup_ticks`, `projectile_speed_mps`, `base_accuracy`, `armour` цели. Здоровье legacy-юнита по умолчанию 1; в новых сценариях задаётся явно.
- Ближний удар после windup при сохранении дистанции наносит `max(0,damage-armour)`; время готовности следующего удара отсчитывается от начала атаки.
- Дальний выстрел: `p_hit=clamp(base_accuracy*archer_skill*(1-distance/range),0,1)`; корректные параметры точности/навыка лежат в [0,1]. Это моя временная формула для испытаний, не точная копия старого D20-баланса.
- При запуске выстрела фиксируется результат проверки попадания; событие прибытия назначается через `ceil(distance/projectile_speed/0.05)` tick. При прибытии мёртвая/отсутствующая цель не получает повторный урон. Промах тоже остаётся событием для отображения.
- Стрелы этой версии — логические события с визуальной траекторией. Укрытия и физическое пересечение летящей стрелы с другим бойцом — отдельный этап после проверки пространственного интерфейса/UE.
- После потерь считается доля живых бойцов относительно состава на начало боя. Порог паники задаёт сценарий. Паника отменяет наступление, запрещает новые атаки и ведёт к `rally_point` своей стороны; невозможный путь оставляет полк на месте в панике. Уже выпущенные стрелы продолжают существовать. Приказы Attack/MoveTo во время паники не исполняются, Withdraw/Rally допускаются.
- Rally требует приказа, живого командира, нахождения в `rally_tolerance_m` от точки сбора и непрерывных `calm_ticks`: без полученного урона и без врага в `rally_safe_radius_m`. Нарушение сбрасывает счётчик; выполнение выводит из паники в Hold. Значения задаёт Scenario, а импорт ставит явные defaults: panic_fraction=0.5, calm_ticks=100, rally_tolerance_m=2, rally_safe_radius_m=20; rally_point задаётся явным параметром стороны, для одностороннего legacy берётся начальный центр её полков с пометкой в отчёте импорта.
- Победа проверяется после применения всех событий шага, урон за шаг не зависит от порядка обхода сторон.

## Вселение без редактора

Проверяется передача управления, а не камера или анимация. `AcquireControl(UnitId)` переводит живого бойца в PlayerControlled; команды ядра управляют им; массовое движение больше не пишет его позицию. Полк и бой продолжают учитывать этого бойца.

При выходе ИИ возвращает солдата к назначенному месту, начиная с фактической позиции. Смерть, смена полка или повторная передача управления имеют явный результат. Переключение не сбрасывает здоровье, экипировку, cooldown и события. Это контракт для будущего PlayerController/Pawn.

Любой внешний ввод, включая позу Pawn, записывается как CommandEnvelope до вызова Step. ExternalPoseSample относится к конкретному tick ядра, для одного бойца берётся последний sequence этого tick; старый tick отвергается. Прямой незаписанный вызов SetExternalPose снаружи runner/адаптера запрещён. Голова симуляции не зависит от реального времени поступления сообщения. В автономном режиме MoveControlledUnit задаёт желаемую скорость, ограниченную параметрами бойца; в UE-режиме поза приходит от Character. Смешивать эти два источника в одном tick нельзя.

## Наблюдение и измерения без GUI движка

Консольная программа запускает сценарий с seed и числом tick, выдаёт снимки, события и итоговую статистику. Нужны save/load и повтор по журналу команд.

Первый визуальный инструмент — SVG вида сверху из записанного снимка: препятствия, границы полков, места бойцов, маршруты, выбранные цели. Обзор нескольких кадров позволяет обнаружить геометрические ошибки. Просмотр полного повтора в HTML — необязательное расширение после рабочего SVG.

Нагрузочные сценарии: 1k, 5k, 10k, 20k бойцов; отдельно марш, перестроение, узкий проход, залпы, плотный бой и массовые потери. Измерять CPU-время шага p50/p95/p99, память, размер/время записи повтора, число проверок и боевых событий. Пока нет рендера, эти измерения не переводятся в игровой FPS.

## Контракт подключения Unreal/Mass

- В первом адаптере ядро — источник истины для жизни, принадлежности, приказов и результатов боя. В Mass хранится ссылка `CoreUnitId` и данные представления. Между ID и `FMassEntityHandle` есть проверяемая таблица соответствия.
- Кадровые снимки читаются пакетно, только после завершения tick. Никаких тысяч вызовов ядро->Actor во внутреннем боевом цикле.
- Перевод метров в сантиметры выполняется ровно на границе адаптера; оси совпадают с выбранными осями ядра. Смерть/создание представлений применяются через отложенные команды Mass.
- Упрощённый/подробный вид одного бойца не добавляет нового участника боя. Смена LOD и удаление Actor из пула не стирают данные бойца.
- Для управляемого Pawn положение/действия поступают в ядро через специальный внешний канал. Один владелец движения на tick. Отдельная защита от одновременного урона ядра и оружейного Actor по одному событию.
- Начальная интеграция однопользовательская. Сеть, предсказание клиента и репликация — отдельная спецификация.
- Адаптер Mass, UHT/UBT, анимация, физика, материалы, отрисовка, взаимодействие с NavMesh и GPU/FPS считаются непроверенными до сборки выбранной версией UE и запуска интеграционных тестов.

## Этапы готовности

1. Ядро, валидируемые сценарии и воспроизводимый шаг.
2. Движение строем, маршруты и наблюдаемый бой двух полков.
3. Офицеры, потери, паника и передача управления, сохранения/повторы.
4. Пакетная оптимизация на 1k/5k/10k/20k, отчёт CPU и контракт адаптера.
5. После появления UE: совместимая сборка, Mass-представление, управляемый Character, навигация/анимация и измерение кадра.

Первые четыре этапа доступны без движка. Это порядок проверяемых результатов, а не обещание календарных сроков или производительности.
